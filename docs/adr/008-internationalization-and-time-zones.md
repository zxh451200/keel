# ADR-008：国际化与时区

- 日期：2026-11-02
- 状态：沿用已选基线；中英与独立显示区域已有源码，独立时区/货币设置及平台验收未完成。

## 背景与依据

依据 `AGENTS.md` §2、§3.1、§5.3，以及 `docs/REQUIREMENTS.md` §3、§9、§10.1。通用桌面 Admin 不能把中文文案、中国格式或某一时区写进持久化业务语义；界面语言、显示区域、时区和币种应分别表达。

核对源码：`lib/core/state/locale_provider.dart`、`lib/core/state/format_locale_provider.dart`、`lib/features/audit/view/{audit_list_view,audit_table}.dart`、`lib/features/diagnostics/view/diagnostics_view.dart`、`lib/features/backup/view/backup_view.dart`、`rust/src/config/mod.rs`、`rust/src/diagnostics/events.rs`，以及 CI 的本地化生成步骤。

## 已选设计与当前实现

1. Flutter 使用 flutter_localizations、intl 与 ARB；简体中文和英文资源分别维护，动态文本、占位符、复数和校验提示都应可翻译。资源通过 flutter gen-l10n 生成 Dart，不手改生成文件，生成本地化文件不入库。Rust 返回稳定错误码，由 UI 映射提示。
2. `language` 支持 zh、en 或空值跟随系统，运行时切换不要求重启。`format_locale` 独立支持 en_US、en_GB、zh_CN 或空值跟随系统；切换语言保留显示区域，不借语言变化修改时区或币种。
3. 系统区域解析保留 en_GB，中文映射 zh_CN，其余未支持区域回退 en_US；通过 WidgetsBindingObserver 监听 locale 变化。该映射是当前有限支持集合，不代表所有地区格式均已实现。
4. 审计、诊断和备份日期读取有效显示区域，通过 intl 格式化；审计分页数字与备份大小使用同一显示区域。备份大小沿用 1024 进制，单位及复数文案由 ARB 提供。
5. 时间点按 UTC epoch 毫秒存储和传递，当前界面使用 `DateTime.fromMillisecondsSinceEpoch` 的本机时区语义显示。显示区域只控制格式；en_GB 不等于英国时区，zh_CN 不等于固定北京时间。
6. 配置 v4 持久化独立显示区域，v1–v3 迁移为跟随系统；Rust 严格校验允许值。保存/导入沿用现有设置锁、写保护与偏好审计边界，不另建国际化状态框架。
7. 时间点与本地日历日期需区分建模；未来金额携带币种语义，精确金额遵循整数最小货币单位的基线，不能用本地化字符串或浮点数作为精确存储。货币、百分比、区域排序须在对应业务接入时落实。

## 替代方案与后果

| 方案 | 取舍与后果 |
|---|---|
| 在 Widget 中硬编码文案、日期模式 | 初期简单，但翻译、复数和区域差异散落；采用 ARB 与 intl。 |
| 让语言决定区域、时区和币种 | 会使英文用户无法保留其他地区习惯，且混淆业务语义；采用独立字段，尚未实现的设置明确保留为待办。 |
| 保存已格式化的本地时间字符串 | 存在歧义，难以跨时区比较；时间点保存 UTC epoch 毫秒，显示时转换。 |
| 立即引入完整时区库及全球地区支持 | 尚无验收和业务边界，不在本轮选型；继续现有本机时区展示与有限区域集合。 |

此设计允许语言与格式分别变化，但要求页面统一读取 provider，新增资源同步补两种语言，并维护配置迁移。跟随本机时区意味着不同机器可显示不同墙上时间；需要跨时区业务时必须显式设计，不能从格式区域推断。

## 未验证、缺口与待外部决策

- Rust/Dart 配置与界面回归已有源码，FRB/l10n 生成及真实构建测试待完成；本次未运行，不能宣称当前完整功能已可构建。
- 系统区域事件、运行时切换、夏令时边界、不同系统时区、布局溢出和 RTL 仍需目标平台测试；当前没有独立时区选择器或完整 RTL 验收结论。
- 更多地区、货币/百分比、语言相关排序与日历日期输入按具体业务接入，不能把当前三个区域当成全球支持声明。
- 业务时区与展示时区的关系、币种集合及金额精度、日期边界/夏令时歧义处理，需产品与业务负责人随实际需求明确。本 ADR 不选择新的时区数据库、货币库或默认业务时区。
