# ADR-011：发布签名与更新策略

- 日期：2026-11-02
- 状态：沿用发布安全基线；Windows 候选证据流水线已有源码，签名、正式发布和更新能力未完成。

## 背景与依据

依据 `AGENTS.md` §0、§7、§11，以及 `docs/REQUIREMENTS.md` §4.4、§7.4–§7.5、§8–§10。发行物需要证明来源、版本和完整性，并保护升级中的用户数据；签名、哈希、SBOM 与扫描分别提供不同证据，任何单项都不证明无恶意行为。

核对实现：`.github/workflows/release.yml`、`.github/workflows/ci.yml`、`scripts/verify.ps1`、`scripts/release_evidence.py`、`scripts/security-check.sh`，以及状态为未执行的 `docs/WINDOWS_RELEASE_CHECKS.md`。

## 已选设计与当前实现

1. 发布候选与普通 PR 测试分开，当前工作流均使用 contents: read，没有签名或正式发布步骤。政策要求发行构建来自受控 CI 和受保护分支/标签，普通 PR/fork 不接触发布凭据、签名私钥或生产机密；私钥不能进入源码、日志或普通产物。
2. 当前 release.yml 在 v* 标签推送时触发，所谓“验证标签来源”步骤仅检查名称前缀。**该 YAML 不证明标签已受保护，也未验证标签所指 commit 属于受保护分支。** 远端 ruleset、授权身份及保护规则的实际配置和效果须由仓库管理员确认并提供证据；既有文档“受保护标签”的措辞应理解为发布前置要求，不能据此认定已完成。
3. 候选流程要求 pub 官方来源及 enforce-lockfile、Cargo fetch --locked，再调用 verify.ps1 -BuildRelease 执行生成、检查、Windows 桥接端到端及 Release 构建，之后单独运行安全扫描。verify.ps1 的 BuildRelease 本身不隐含 Security，不能省略工作流后续安全步骤。
4. 当前组装 Windows x64 目录式 ZIP，包含 exe、DLL、data、LICENSE、THIRD_PARTY_NOTICES、CHANGELOG，并检查 Flutter NOTICES.Z。由 Cargo metadata 与 Dart pub deps 生成 SPDX 组件/文件清单、SHA256SUMS 和构建元数据，工作流上传候选及安全报告 artifact，保留 30 天；没有创建公开正式发行版。
5. 生成证据的能力与生成证据的实际运行分开。SHA256SUMS 当前覆盖生成证据前枚举的应用文件，不是最终 ZIP 的独立哈希；SPDX 的 Cargo 许可来自元数据，Dart 许可为 NOASSERTION。最终候选包哈希、SBOM 完整性和正式来源仍需按发布清单核验；哈希与这些 JSON 不等于签名或 attestation。
6. Windows 沿用 Authenticode 规划，覆盖 exe、DLL 和安装器，启用后验证签名及时间戳；证书与时间戳成本单列决策。当前未实现签名，不能宣称候选已签名。签名用于发布者身份和签名后完整性，不能代替 Defender、依赖审查和运行验收。
7. v1 不实现静默自动更新。未来若实现，沿用已定安全约束：更新清单由发布密钥签名，客户端核验签名、版本、平台及 SHA-256，来源不符、校验失败或回滚异常即拒绝；不提供强制绕过、不执行远程脚本、不从固定域名外下 DLL、不自动提权，配套轮换、撤销、停发及恢复备份。
8. 升级沿用 SemVer、兼容/迁移说明与 CHANGELOG；程序目录和用户数据分离，迁移前备份，升级/卸载不误删数据。发现依赖/Defender/SmartScreen 告警暂停发布，保存对象、版本、时间、工作流和哈希，必要时撤回、轮换凭据并发布修复，不要求用户关闭安全软件或忽略未知发布者。

## 替代方案与后果

2026-11-05 源码增量：候选组装后调用 `collect_signature_evidence.py`，
从 Windows SDK 版本目录定位 x64 SignTool，缺工具、未签名、警告或失败均阻断。
打包后调用 `verify_signature_evidence.py` 核对可信报告的 commit、目标覆盖和文件哈希。
候选上传要求两个阶段成功，并保留报告及状态。63 项 Python 回归和 YAML 语法检查通过，
Windows/PowerShell/SignTool/Actions 未运行。未实现签名或发布者允许名单；
报告 JSON 自身不构成可信来源，离线核对不能代替重新验签或 attestation。

| 方案 | 取舍与后果 |
|---|---|
| 从开发机目录或聊天附件直接分发 | 缺少一致证据和来源约束；采用受控候选流程，正式官方渠道仍待落实。 |
| 用 SHA-256 代替签名/发布身份 | 能比对内容但无法独自证明发布者；保留不同层次证据，不混称已签名。 |
| 立即选择证书供应商或安装器 | 存在成本、密钥保管和许可待决项；继续既有 Authenticode 规划与目录式候选，不新增供应商选择。 |
| v1 静默更新或验签失败后仍允许安装 | 增加供应链与数据恢复风险，违背基线；v1 保持无静默更新，未来按明确验证边界设计。 |

候选先产出可检查证据，便于独立审核，但 artifact 不是正式分发渠道，人工验收和保护规则仍需要维护者落实。保留用户数据提高升级恢复能力，也要求持续维护迁移、备份及兼容测试。

## 未验证、缺口与待外部决策

- 本次没有运行发布工作流，也没有核验远端标签/分支保护；不能宣称流水线成功、来源受保护或 Windows/Linux 平台支持已验收。
- Windows 签名证书类型/供应商、预算、时间戳服务、密钥保管与授权责任需外部决策；本 ADR 不选新方案，也不把待决理解为自动豁免发布门禁。
- attestation 的生成与验证、Defender 日期/引擎/结果记录、干净环境首次运行、安装/升级/卸载/重装和发布后签名验证均未完成。
- 正式官方分发渠道、证据长期留存、仓库保护配置、发布/撤回责任人与凭据轮换流程尚待维护者落实。安装器、Linux 包格式和发行版范围仍未选定或验收。
- 未来更新服务、算法/密钥格式、域名和客户端实现需单独设计评审；现有约束不代表更新器已经存在。当前 FRB 生成和新增依赖锁定仍待完成，阶段 0 历史构建结果不构成当前候选放行依据。
